# Employee Mode 初回プレイ感想と改善案

記録日: 2026-09-29  
対象: v0.1 Employee Mode の初回プレイ

## プレイ時の感想

ユーザーからのコメント:

> 一回だけだったけど、パワーの関係もあって、Waitがほとんどになってしまった。あまり代わり映えのない日が多いので、できることが少ない印象。画面が縦に長過ぎてスクロールが必要なのは、ちょっと縮めたい。

添付されたDay 30画面では、Banked Reset 2回、Global Reset 2回、Reset Cost 220、残りReset Energy 40を確認できる。したがって、Resetを一度も使えないプレイではなく、Resetの機会以外の日にWAITが続き、日ごとの変化も弱く感じられたという初回所感として記録する。

## 現行仕様との関係

- Player Actionは `WAIT`、`BANKED_RESET`、`GLOBAL_RESET` の3種類。既存EngineとIntegration Contractで固定されている。
- 初期Reset Energyは40、Settlementごとの増加は8。Banked Resetは30、Global Resetは80を消費する。
- Random Eventは1日あたりの抽選率22%、最大1件。現行イベント定義は少数に絞られている。
- `docs/handoff/logic/UNRESOLVED.md` でも「WAITがほぼ無意味になっていないか」をプレイテスト観察項目としている。
- 今回は1周の所感であり、Balance変更や新しいPlayer Actionの採用判断を確定する材料とはしない。

## 対策案

### 1. 画面をコンパクトにする

ゲーム画面の余白、パネル内間隔、ゲージ行の高さ、Incident Logの表示量を詰める。デスクトップでは主要な操作と状態をより小さい縦幅に収め、EndingはDay 30時だけ表示する。スマートフォン幅では読みやすさと操作サイズを保ち、縦スクロールを許容する。

これはGame EngineやBalanceを変えないため、先に検討しやすい案。

### 2. WAIT中にも次の判断材料を見せる

Reset Energyの次回加算量と、Banked / Global Resetが使用可能になるまでの目安を表示する。Pressureの変化、当日のイベント、WAIT後のSettlement予測をIncident LogやChappy欄で短く説明し、「何も起きない日」に見えにくくする。

表示だけの変更では選択肢そのものは増えないが、貯める判断と各日の結果を読み取りやすくできる。

### 3. Balanceとイベントの調整は追加プレイ後に判断する

複数のプレイ方針で数周し、WAIT・Banked・Globalの選択回数、Reset Energyの推移、イベント発生数、満足度・不満度を比較してから、既存のEnergy gain / Reset cost / Event chanceを調整する。初回の感想だけで値を変更すると、別の方針を不利にする可能性がある。

これは検証済みBalance成果物の変更になるため、Project Controlの採用判断後に行う。

### 4. 新しいPlayer Actionは現時点では追加しない

新しい行動は固定済みのAction契約とv0.1範囲を広げる。まず既存3行動の見せ方と、暫定とされているBalance値を検証する。新Actionは、既存の調整では退屈さを解消できないことが確認されてから別途検討する。

## 推奨する検討順

1. デスクトップ画面の縦幅を詰める。
2. Reset Energyの到達目安とWAIT後の短い結果説明を表示する。
3. 複数プレイの記録を比較する。
4. 必要が確認できた場合のみ、Balance / Eventの変更案をProject Controlへ提示する。

## 状態

この文書はプレイテストの記録と提案であり、実装承認やBalance変更の指示ではない。今回の記録に伴うゲームコード、CSS、Engine、Balance、Event定義の変更は行っていない。

### 追加で出たアイディア

#### Krogのモニターに、穏やかな日も含めてもっとユーザーの声を出す

Xの雰囲気は大きな事件や高い不満のときだけ発生するものではない。現在の実装はゲーム状態・イベントタグに対応する架空の短文を選ぶ構造だが、初回プレイでは落ち着いた投稿が続き、コミュニティの存在や日ごとの違いが弱く見えた。

次の案として、calmを含む各状況に複数の架空投稿を持たせるほか、短い投稿を複数件流す形を検討する。投稿内容は実在のX投稿を取得・転載せず、既存仕様どおり静的なフィクションとする。投稿頻度や件数は画面の情報量を増やしすぎないよう、UIの縦幅見直しと合わせて決める。

#### Tyboによる「口先介入」をプレイヤーの判断候補にする

TyboがXへ書き込み、反応を見て状況を動かそうとする行為を、単なるランダムイベントではなくプレイヤーの介入として扱う案。たとえば期待をあおる／火消しを試みる／様子を見る、といった投稿と、その後のユーザー反応をゲーム内で表現する。

これは現在の3種類のPlayer Action（WAIT、BANKED_RESET、GLOBAL_RESET）を増やす可能性があるため、v0.1の固定済み契約へは追加しない。ゲーム内で何を消費し、いつ効果が出て、期待値・不満・Krogの反応にどう作用するかは、次期候補として別途設計判断が必要。

#### Banked Resetの通常時の利用頻度をGlobal Resetより低くする

ユーザーの考えとして、Banked Resetは通常時にはGlobal Resetより使える頻度が低い方が自然であり、通常のコスト設定だけでBanked Resetが先に何度も使える状態はバランス上おかしく感じられる。臨時エネルギーの特配など、不定期イベントで一時的にBanked Resetが使いやすくなる例外はあり得る。

現行値では、Banked Resetのコストが30、Global Resetが80、SettlementごとのEnergy増加が8であり、初回画面でもBankedの方が早く到達可能な設定になっている。この差をどう改めるか（コスト、供給方法、回数制限など）はまだ決めない。Balanceを変更する場合は、複数方針・複数seedで頻度と結果を比較し、GLOBAL RESETの特配イベントを含む例外設計と合わせてProject Controlで判断する。

## 追加アイディア: WAIT時のTybo投稿とゲーム内ヘルプ

追記日: 2026-09-29  
位置づけ: ユーザーとの追加検討メモ。採用・実装は未決定。

### WAIT日にTyboの投稿を選ぶ

WAITを選んだ日にも、TyboがXへ書き込む内容を数パターンから選べる案。例として、RESETを期待させる発言、状況を見守る発言、明言を避ける発言などが考えられる。書き込みによってユーザーのExpectationやFrustration、Krogの投稿が変わる可能性がある。

この選択が単なる台詞選びなのか、WAITに付随するゲーム上の介入なのかは未決定。期待を高める発言には、将来RESETを実施できなかった場合の反動を持たせるかも含めて検討する。Player Actionを増やす場合は、v0.1の固定済みAction契約から分けた次期機能として設計する。

### 呼び出せる簡易ヘルプ

ゲーム画面から必要なときに開ける、短い遊び方ページまたはヘルプ表示を用意する案。少なくとも、1日の進行（Pressure → Player Decision → Settlement）、WAIT / Banked Reset / Global Resetの違い、RESET Energyと各コスト、Global ResetのHOLD操作、30日終了と最終レポートを説明候補にする。

通常画面の情報密度を上げずにルールを確認できるよう、ヘルプの呼び出し位置や表示形式（別ページ、モーダル、折りたたみ表示など）はUIの縦幅縮小案と合わせて決める。

これらも提案段階であり、WAITの挙動やUIは変更していない。
